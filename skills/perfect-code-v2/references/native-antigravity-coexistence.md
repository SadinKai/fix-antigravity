# Native Antigravity and Cross-Skill Coexistence

Read this reference before coordinating native planning/parallelism, a fresh-context verifier, or another core responsibility.

Perfect Code owns the engineering contract and evidence. It does not recreate platform topology or another skill’s state.

Manual invocation on documented Antigravity surfaces is `/perfect-code-v2`. The `$perfect-code-v2` form is retained only for hosts that support the optional `agents/openai.yaml` metadata contract.

## Native Antigravity

### `/plan`

Consume an approved native plan. Map its steps to acceptance and evidence as work proceeds. Reopen planning only when new evidence invalidates a material premise; update the existing plan rather than creating a competing master plan.

### `/boost`

Use for decomposable complex engineering where workers can inspect genuinely independent subsystems, hypotheses, or evidence lenses. Give each worker a bounded question and output contract. Keep one lead, one coverage ledger, and one final status owner.

Do not use Boost merely to multiply generic reviews.

### Teamwork

Use for true long-horizon or multi-agent work. Perfect Code defines the engineering acceptance/evidence contract for its assigned scope. Continuity & Recovery, when available, owns the durable cross-session state.

### Subagents and fresh-context verification

Use conditionally for independent investigation or verification. Send:

- actual task and acceptance contract;
- final relevant artifacts or bounded context;
- evidence already available without the author’s persuasive narrative;
- exact verification scope;
- non-overlapping output contract.

One pass is normally enough. Another requires new material evidence, a newly discovered high-risk surface, or a materially different oracle. Findings must be reproduced or otherwise supported before acceptance.

### Browser and Chrome DevTools

Use native browser/DevTools for actual UI, network, console, accessibility, performance, and interaction evidence. Source inspection is not a substitute for observed browser behavior.

### MCP

Use connected tools/data when they are the authoritative or live source. Validate permissions, provenance, result scope, and mutation effects.

### Rules, hooks, permissions, validators

- Persistent invariants belong in rules.
- Deterministic enforcement and recording belong in hooks when configured.
- Action boundaries belong in permissions.
- Tests, type checking, builds, linters, scanners, profilers, and other validators are evidence sources.

The skill may recommend or invoke available mechanisms within authorization; it does not implement substitutes in prose.

## Other core responsibilities

### Evidence Research

Request a bounded external claim when current source truth materially affects engineering. Perfect Code retains responsibility for applying the evidence to the repository. If the skill is absent, research directly and label provenance/limits.

### Continuity & Recovery

Hand off durable objective, constraints, decisions, live/invalidated hypotheses, evidence validity, changed artifacts, remaining claims, failed strategy classes, blockers, and next safe action. Perfect Code’s in-task coverage notes do not become a second canonical memory.

### Risk & Change Assurance

Escalate security-sensitive, privacy-affecting, production-facing, destructive, migration, release, rollback-dependent, financially/legal consequential, or otherwise externally effective work. Perfect Code can establish technical facts but does not grant authorization or claim production observation.

If the other skill is absent, preserve the boundary and return `BLOCKED`, `UNVERIFIED`, or the exact engineering-only state where necessary.

## Composition invariants

- One lead workflow per phase.
- One canonical durable state owner.
- One current verified repository/system state, reconciled by Continuity when that workflow is active.
- One engineering owner per material change and one Evidence owner per material external claim.
- One owner for final engineering completion.
- Reuse another owner's valid evidence by pointer; do not silently repeat the work or overwrite its conclusion. Later applicable evidence must explicitly supersede stale evidence.
- Supporting work returns bounded evidence, not a second plan or generic done verdict.
- Parallel workers partition by surface, hypothesis, or evidence lens.
- A disagreement is resolved by evidence, not agent vote.
- Engineering completion is only the engineering layer. It does not imply research completion, authorization, a passing consequential gate, or overall task completion.
- Missing integration capability reduces the completion claim; it does not authorize invention.
